## High

### H1 — The word-timing cache bakes in where the block sat in the section

`audio.py:657` composes word timings with `offset_ms=timing.speech_start_ms`,
so what `audio.py:668` writes to `<key>.words.json` is **absolute within the
section**. The key is `_cache_key(text, engine, voice, speed)` — it says
nothing about position. `WORDS_CACHE_SUFFIX`'s own comment and
`cache.cached_renders`'s docstring both claim the two files "are a function of
exactly the same inputs". They are not.

So any rebuild that changes an earlier block's duration hands every later
block the previous build's offsets. Edit one paragraph, change one
pronunciation rule, switch a quote voice: the audio for the unchanged blocks
is correctly reused, and their word highlighting is silently wrong for the
rest of the section.

Reproduced — two blocks, only the first one's text changed between builds:

```
build1  block b0-1 speech_start_ms = 1350
build1  first word start_ms        = 1350
build2  block b0-1 speech_start_ms = 7350
build2  first word start_ms        = 1350   <- 6000 ms adrift
```

`test_align_article_reads_cached_words_without_recomputing` does exercise the
cache-hit path, but with the *same* article both times, so every
`speech_start_ms` is identical and the bug cannot show.

Fix: cache the clip-relative timings and add `speech_start_ms` on read, not on
write. The write becomes `offset_ms=0` and the two read paths (cache hit and
fresh align) both shift afterwards.

### H2 — Nothing clears `block.words` when an article is rebuilt

`db.save_word_timings` (`db.py:484`) is the only writer of `block.words` in
the tree. `save_manifest` updates `start_ms`, `dur_ms`, `speech_ms` and
`speech_start_ms` and leaves `words` alone; `forget_audio` nulls the first
three and leaves `words` and `speech_start_ms` alone, under a docstring that
says "stale ones are worse than none".

Build an article with `word_highlight` on, then turn the toggle off and
rebuild with a different voice. `save_manifest` writes the new block timings,
no align job is queued, and `block.words` still holds the old voice's
absolute timings. `build_payload` filters on `start_ms IS NOT NULL` only, so
the reader serves them and the player highlights words against audio they were
never measured on.

Fix: clear `words` in `save_manifest` (a build invalidates them by
definition) and in `forget_audio`. The align job writes them back afterwards
when it runs.

### H3 — A job whose child dies is requeued for ever, with no backoff

`_run_in_child` (`jobs.py:263`) sees a non-zero `exitcode`, calls
`_requeue_orphans(kinds)`, and returns `True`. `_loop` only sleeps when
`_run_in_child` returns `False`, so it immediately spawns another child, which
claims the same job, and dies the same way. The `job` table has no attempt
counter (`schema.sql:111`), so nothing ever gives up.

Anything that reliably kills a child — the OOM killer, a malformed block that
crashes a C extension — becomes a continuous respawn loop, each iteration
paying a full model load. On this box that is minutes of CPU per cycle,
indefinitely, with the only evidence a repeated `the build process exited
with -9` in the log.

Fix: an `attempts` column, incremented in `_requeue_orphans`, and a job
marked `failed` past two or three. H4 is the most likely trigger.

### H4 — Viterbi memory grows with the square of a block's duration, uncapped

`_viterbi_align` (`tts/aligner.py:368`) allocates `alpha` as
`(frames, 2*chars+1)` float64 plus a `backptr` of the same shape in int8.
Frames scale with duration and characters scale with duration, so the pair is
quadratic:

| block speech | `alpha` + `backptr`, per thread |
| --- | --- |
| 30 s | ~13 MB |
| 60 s | ~53 MB |
| 120 s | ~208 MB |

`align_article` runs `concurrency=settings.build_concurrency()` of these at
once — 4 on this box — over one shared session, so the peak is four times a
column.

This is not hypothetical. The longest block in `data/textcast.db` today is
2,693 characters, 2,684 after `to_target_text`, which is about three minutes
of speech: **~370 MB of `alpha` plus ~46 MB of `backptr`, and ~1.7 GB across
four threads**, on top of the ONNX session and whatever the web app is
holding. 27 blocks in the library are over 1,500 characters.

Fix, cheapest first: `float32` for `alpha` halves it and costs nothing at
these path lengths; a length cap above which a block falls back to
block-level highlighting bounds it properly; a banded or chunked decode fixes
it. Whichever is chosen, H3 should be fixed too, or an OOM here becomes the
respawn loop.

## Medium

### M1 — `service.fetch` has no size cap and no content-type check

`service.py:72-84` calls `netguard.get` with no `stream`, no cap, and returns
`response.text`. `response.apparent_encoding` on the fallback path runs
`chardet` over the whole body as well.

Uploads are capped (`_read_capped`, `BodySizeLimit`) and pictures are capped
(`pictures.MAX_BYTES`, read incrementally and abandoned at the cap, with the
reason written into the comment). The URL path — the bookmarklet, the
Shortcut, a link in a newsletter — is the one outbound read left unbounded,
and it runs inside the web request. A link that points at a large file, by
malice or by a mislabelled `Content-Type`, is the whole body in the app
process.

Fix: `stream=True`, the same chunked read-to-cap `pictures._download` already
has, and a `Content-Type` check for `text/*`.

### M2 — `_generate_emissions` mis-sizes its window and then aligns against the wrong frames

`window = int(window_length * SAMPLE_RATE)` (`tts/aligner.py:308-311`) where
`window_length` is `len(waveform) / SAMPLE_RATE`. Float division followed by
multiplication does not always round-trip: for about **0.9% of sample counts**
between 2 s and 22 s, `int()` truncates to `len(waveform) - 1`. First few:
32001, 32004, 32007, 32010, 32013.

When that happens, `extension` becomes nearly a whole window and `n_windows`
becomes 2. The multi-window path is then wrong twice over:

- `total_audio_s = window_length * n_windows + 2 * context_s` undercounts the
  audio actually encoded, which is `n_windows * (window_length + 2*context_s)`.
  With a 2 s window it overestimates `frames_per_sec` by 1.5×, so
  `context_frames` trims three times too much off each end.
- The context frames *between* the two windows are never trimmed at all — they
  sit in the middle of the concatenated emissions as duplicated audio.

`stride_ms` is derived from the final frame count, so the average rate still
looks right and nothing raises. The block gets silently wrong word timings
rather than falling back to block-level highlighting, which is the one failure
mode the design's degradation section rules out.

Fix: `window = len(waveform)` when no explicit `window_length` was passed —
one window, exactly the clip, which is what the docstring already describes.
The multi-window arithmetic should be corrected or removed rather than left as
a path nothing intends to reach.

### M3 — `align_article` leaves stale words in place on every early return

`load_manifest` pre-fills `BlockTiming.words` from the database, and
`align_article` overwrites `timing.words` only on success. Four paths return
without touching it: block not found, empty spoken text, `pcm_path` missing
(`audio.py:645`), and `AlignmentError`. `save_word_timings` then writes those
pre-loaded values straight back, under a docstring promising that a block with
no words for this build "is set to NULL rather than left holding a stale array
from a previous build".

So a block whose alignment fails on the second build keeps the first build's
timings against the second build's audio. Related to H2 but separate: this one
is inside the align lane's own logic.

Fix: `timing.words = []` at the top of `align_one`.

### M4 — `_zip_response` holds the archive three times over

`web/app.py:2121-2136` writes into a `BytesIO`, then `buffer.getvalue()`
copies the whole thing, then hands that to `Response`. For
`/api/export/audio.zip` — the whole `media/` tree, already-compressed Opus, so
DEFLATE buys nothing — that is 3× the library's audio resident in the web
process. The docstring says "a few hundred megabytes at most, so nothing here
streams. Measure before that stops being true"; the measurement is that the
peak is three times the number in that sentence, not one.

Cheapest fix without streaming: pass `buffer.getbuffer()` instead of
`getvalue()`, dropping one copy. Streaming with `zipstream` drops the rest.

## Low

### L1 — The ingest route parses the whole multipart body before checking the key

`_ingest_key_in_request` (`web/app.py:176`) reaches `await request.form()`
before `secrets.compare_digest`. Starlette spools a multipart body with no
size limit of its own, and `BodySizeLimit` only turns away a request that
*declares* its size. An unauthenticated caller inside the `INGEST_ATTEMPTS`
budget can make the app spool an arbitrary chunked body. Bounded by the
limiter, so slow rather than free.

Fix: reorder — check the `x-textcast-token` header first (already done), and
gate the form parse on the declared content-length.

### L2 — The service worker can cache the login page under an article's URL

`sw.js:352` stores a navigation response into `OFFLINE` when `response.ok` and
the URL is already held. `fetch` follows redirects, so an expired session
turns a GET of `/a/<slug>` into a 200 for `/login`, which is then stored as
the article's offline page. On the next flight the reader opens their kept
article and gets a sign-in form.

Fix: `if (response.ok && !response.redirected && request.mode === "navigate")`.

### L3 — `netguard.get` never closes its `Session`

`netguard.py:108` builds a fresh `requests.Session` per call and returns
without closing it on any path, and mounts a new adapter per redirect hop.
CPython's refcounting collects it soon after, so this is untidiness and a lost
connection pool rather than a durable leak — but it means no fetch ever reuses
a connection, and the shape is one `try/finally` away from being right.

### L4 — `_ensure_file` leaves `.part` files nothing collects

`tts/aligner.py:92` writes to `<name>.<pid>.part` and replaces on success. A
failed or killed download leaves the part file in `settings.aligner_dir`.
`cache.sweep_cache` only walks `settings.cache_dir`, so nothing ever collects
these. Small and rare; worth a line in the sweep for symmetry with the block
cache, which had exactly this problem.

### L5 — `log_probs` normalises without subtracting the max

`tts/aligner.py:339`:
`emissions - np.log(np.sum(np.exp(emissions), axis=-1, keepdims=True))`.
`np.exp` on a float32 array overflows to `inf` above about 88, which turns the
whole row into `-inf` and the alignment into `AlignmentError` (so it degrades
rather than lying). Realistic wav2vec2 CTC logits sit well under that, so this
is a robustness smell rather than an observed failure — but the max-subtracted
form is one line and removes the question.

### L6 — `wordAt` never lets a word expire

`player.js:162` returns the last word whose start has passed, and never
consults `dur_ms`. Through the trailing pause after a block's last word — the
`gap_ms` before the next block starts — that word stays lit. It reads as the
voice lingering on a word it has finished. A `start + dur` check would clear
it; whether that is better than a word staying lit is a judgement to make by
listening, not by reading the code.

### L7 — `limits._sweep` re-sorts every key on every call once over the cap

`web/limits.py:98` sorts all `max_keys` entries to evict, on every single
call, once the table is full — and skips the current key while still
subtracting it from the count, so the table can sit permanently one over the
cap and sort for ever. 4096 entries is a small sort, and the route is
rate-limited, so this is a sharp edge rather than a problem.

### L8 — `_wrap_rich` trusts that `rich`'s text equals `text`

`web/wordwrap.py:47` walks `rich`'s text runs using ranges computed against
`text`. `find_word_ranges` validates against `text` only. If the two ever
disagree — a sanitizer change, a `rich` that carries a caption the plain text
does not — the offsets drift and the highlight lands on the wrong words
silently, instead of taking the documented fallback. A length comparison
between `text` and the unescaped concatenation of `rich`'s text tokens would
turn a silent wrong answer into the fallback the module already has.

### L9 — `test_word_level_highlight_moves_forward_with_the_clock` is flaky

Fails in the full run (`1 failed, 782 passed in 293.79s`) with
`Page.wait_for_function: Timeout 10000ms exceeded`. Passes three times out of
three on its own, and passes with the whole of `tests/test_player.py`
(54 passed). So it is load-sensitive, not broken.

The likely mechanism is `offsetMs()`: the player measures
`AudioContext.outputLatency` asynchronously, and if that measurement lands
between the seek and the assertion the highlighted index moves off `'2'`. A
test that pinned the offset to zero before seeking would not care how loaded
the box is.

## Not filed as findings

Checked and found sound, recorded so a later pass does not re-derive them:

- **Path handling on `/media/{slug}/{name}`.** `%2F` is decoded by uvicorn
  before Starlette's `[^/]+` matches, so a slug cannot carry a separator, and
  `..` is refused explicitly.
- **`db.connect` in the align progress callback.** It is thread-local and
  cached, not a connection per call.
- **`claim_job`'s article exclusion** covers the align lane too, so
  `service.delete`/`reparse`/`delete_audio` cannot race an in-flight
  alignment.
- **`payload|tojson` in `reader.html`.** Jinja's `tojson` is
  `htmlsafe_json_dumps`; `<`, `>`, `&` and `'` are escaped.
- **`_export_name`** replaces `/` before it becomes an arcname, so a hostile
  page title cannot write outside the zip root.
- **`mail.fetch`** uses `with imaplib.IMAP4_SSL(...)`.
